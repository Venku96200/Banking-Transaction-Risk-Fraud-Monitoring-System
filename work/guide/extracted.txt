1. Project Overview
Project name: Banking Transaction Risk Monitoring & Anomaly Detection Platform
The project simulates a banking risk-monitoring environment in which a stream of customer
transactions is analyzed for unusual behavior. The system combines deterministic risk controls with
machine-learning anomaly detection, converts the signals into an interpretable 0–100 risk score,
creates alerts, and gives a risk analyst a dashboard for investigation, review and escalation.
Important: this is an educational/synthetic-data project. It is not an AML/compliance system, does not use
real customer data, and should not be presented as production financial-crime software.
Why this is a strong CRDP project
• Maps directly to risk identification, assessment, monitoring, reporting, controls and escalation.
 
• Uses your existing Python, SQL, FastAPI, JavaScript and ML skills rather than requiring a completely
 new stack.
• Demonstrates that you understand why risk systems need both rules and statistical/ML signals.
 
• Creates strong interview material around false positives, false negatives, explainability, thresholds,
 controls and model monitoring.
• Complements your existing Customer AI project instead of duplicating another generic prediction
 problem.
Target outcome
Build an end-to-end application where a transaction can travel from raw data → SQL storage → feature
engineering → rule engine + Isolation Forest → risk score → alert → analyst review →
escalation/outcome tracking.

3. Functional Requirements
3.1 Transaction ingestion
• Accept transaction records through a CSV import and/or POST /transactions endpoint.
 
• Validate required fields, timestamps, amount ranges and identifiers.
 
• Persist valid transactions in SQL.
 
• Reject malformed records with a useful validation message.
 
3.2 Customer behavioral baseline
• Calculate historical average transaction amount.
 
• Calculate amount standard deviation and transaction frequency.
 
• Track usual locations and devices.
 
• Track typical transaction hours.
 
• Use previous transactions to create behavioral features.
 
3.3 Risk assessment
• Run deterministic controls such as unusually large amount, new device, new location and rapid
 transactions.
• Run an Isolation Forest anomaly detector.
 
• Normalize and combine rule and ML signals.
 
• Generate a risk score and risk level.
 
• Store the reasons that contributed to the score.
 
3.4 Alert management
• Create alerts for High and Critical transactions.
 
• Allow filtering by risk level, date, customer and alert status.
 
• Allow an analyst to mark an alert as reviewed, false positive or escalated.
 
• Store review notes and timestamps.
 
3.5 Dashboard
• Show total transactions and alert counts.
 
• Show risk distribution.
 
• Show risk trends over time.
 
• Show top high-risk customers/transactions.
 
• Provide drill-down into transaction-level explanations.

7. Rule-Based Risk Engine
Rules are deliberately transparent. Each rule should produce both a score contribution and a
human-readable reason. This makes the system easier to audit and explain than a black-box prediction
alone.

Example implementation
def calculate_rule_risk(tx, profile):
    score = 0
    reasons = []
    if tx.amount > 5 * profile.avg_amount:
        score += 25
        reasons.append("Amount is >5x customer average")
    if tx.device_id not in profile.known_devices:
        score += 20
        reasons.append("New device detected")
    if tx.location not in profile.known_locations:
        score += 20
        reasons.append("New location detected")
    if tx.hour not in profile.normal_hours:
        score += 10
        reasons.append("Unusual transaction hour")
    if tx.velocity_10m >= 5:
        score += 15
        reasons.append("High transaction velocity")
    return min(score, 100), reasons
Design principle: controls should be configurable
In the first version, rules can live in Python. A stronger second version stores rule thresholds and
weights in a risk_rules SQL table so that the risk engine can be configured without rewriting business
logic.

Why the hybrid design is useful
• Rules provide deterministic controls and clear reasons.
 
• ML can discover unusual combinations that rules did not explicitly encode.
 
• The combined score creates a single operational signal for prioritization.
 
• Analysts can still inspect the underlying reasons instead of receiving only a probability.

15. Security & Responsible Design
Because the domain is banking, security and responsible data handling should be part of the project
story even if the application uses synthetic data.
• Never commit API keys, database passwords or secrets; use environment variables.
 
• Use parameterized queries/ORM operations to reduce SQL injection risk.
 
• Validate and sanitize uploaded files.
 
• Do not expose unnecessary customer fields in API responses.
 
• Use authentication and role-based access control as a stretch feature.
 
• Log security-relevant events without logging sensitive credentials.
 
• Use synthetic data only; never upload real customer information to the repository.
 
16. Known Limitations
• Synthetic transaction behavior does not represent real banking behavior.
 
• Isolation Forest is an anomaly detector, not an AML decision engine.
 
• Risk scores are project-defined and have no regulatory meaning.
 
• The project does not establish that a transaction is criminal or fraudulent.
 
• Real production systems require governance, validation, model risk management, privacy controls
 and domain expertise.

19. Interview Preparation
Why did you use Isolation Forest?
Answer: Because the problem is anomaly detection and labels may be incomplete or synthetic.
Isolation Forest can learn patterns of normal behavior and identify observations that are easier to
isolate.
Why combine rules and ML?
Answer: Rules provide deterministic, auditable controls and explanations. ML adds the ability to detect
unusual combinations not explicitly encoded by rules.
Why not use accuracy?
Answer: With imbalanced risk events, accuracy can be misleading. Precision, recall, false-positive rate
and the operational alert burden are more informative.
What is a false positive here?
Answer: A normal transaction incorrectly flagged as risky. Too many false positives can overwhelm
analysts and reduce trust in the monitoring system.
What is a false negative?
Answer: A genuinely anomalous transaction that the system fails to flag. In risk monitoring, missed
cases can be particularly costly.
How did you generate your data?

Could the risk score prove fraud?
Answer: No. It is a prioritization signal. A high-risk score means the case deserves attention; it does not
